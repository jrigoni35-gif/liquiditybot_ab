# Session 2026-08-30 — the audit wave

The same day cut #9 minted era-6 ([[synthesis/comparability-boundaries]] row 9,
[[synthesis/progression-bar]] PRESTIGE #2), a general-update audit wave ran
across the measurement plane. Everything below is **SAFE class** — none of it
touches which orders are placed or how they fill — with one exception that is
**docketed BECAUSE it is cohort-resetting** (§4).

Primary artifacts, all in `liquiditybot_ab`:
`docs/HANDOFF.md` (WATCH LIST · OPERATOR DECISIONS OWED · OWED-VERIFY register
· the DELIVERY-1 row), commit **`8f27a326`**, `docs/grafana/*.yaml` (4 files),
`ml/registry.py`, `ml/meta_model.py`, `scripts/cohort_eval.py`.

**Paper/real boundary** (domain rule 9): §3 is a count of **simulated** fills;
§1, §2 and §4 are **repo-side / infrastructure-side** and involve no market
data at all. Nothing here is venue truth.

## 1. The pager was silent for 47 days — found, fixed, and then PROVEN by an organic firing

**The outage.** Both pre-existing Grafana alert rules (`lb-telemetry-stale`,
`lb-manip-high`) had carried **`notification_settings: null` since creation on
2026-07-14**, and the root notification policy's receiver is `"empty"` — a
receiver with **zero integrations**. **Any firing between 2026-07-14 and
2026-08-30 paged nobody: 47 days.** [K]

The most uncomfortable detail is that the repo had already found it. The
project's own `docs/grafana/liquiditybot_deadman_alert.yaml` **dated this
2026-08-17 and labelled it "MANUAL-APPLY"** — and it was never applied. A
correct diagnosis, written down, that nobody executed, is
[[concepts/adoption-is-not-enforcement]] in its purest form; the note aged
into decoration.

**The fix** (`8f27a326`, SAFE, no code changed): the documented
read-modify-write PUT setting `notification_settings.receiver =
grafana-default-email` on both rules, verified live by a GET after the PUT.
The same commit closed the repo/cloud drift both ways — `lb-drift-stuck` and
`lb-brier-degraded` PROVISIONED live from YAMLs that had never been applied
(POST 201, folderUID `liquiditybot-ops`, group `liquiditybot-ml`, interval
60s), and the live-only `lb-manip-high` exported back to a new
`docs/grafana/liquiditybot_manip_alert.yaml`.

**The proof, and why it is worth more than a test email.** Delivery was
closed by an **ORGANIC** firing — **nothing artificial was sent**:

| what | value |
|---|---|
| rule | `lb-drift-stuck` |
| alert `startsAt` | **2026-08-30T23:04:30Z** |
| mailer `lastNotifyAttempt` | **2026-08-30T23:05:05.164Z** (35s later) |
| `duration` | **341ms** |
| `error` | **None** |

Read from `GET /api/alertmanager/grafana/config/api/v1/receivers` — **a
zero-cost read of the dispatch record**. This corrects a method claim the
lane itself had made: *"only a real send closes that"* is **FALSE as a general
statement**. It was true at 22:44Z, when nothing had ever fired and the
endpoint therefore held no dispatch record; it stopped being true the moment
any rule fired. That GET is now the check to run FIRST, before ever
considering the operator-gated DELIVERY TEST block (which does send real mail
and stays not-run-unattended).

**The residual that genuinely survives, unclosed.** `error=None` proves only
that Grafana Cloud's mailer **ACCEPTED the handoff**. It does **not** prove
gmail delivered to the INBOX rather than spam, and it does not prove the
mailbox is monitored. Zero-cost close, operator-side: eyeball that inbox *and
its spam folder* for an `lb-drift-stuck` mail stamped ~23:05Z.
Registered as [[synthesis/owed-measurements]] **item 109**.

> [!danger] **STILL-ARMED TRAP — an OPERATOR DECISION OWED, not Claude's.**
> The root route **still** points at receiver `empty` (0 integrations). The
> fix was deliberately a **per-rule override** (smaller blast radius than a
> policy-tree change), which means **the 4 current rules deliver only because
> each carries its own `notification_settings`.** Any rule created without
> it routes to the void **exactly as the 47-day outage did**. Fix is either
> (i) repoint the root route at `grafana-default-email`, or (ii) mandate
> `notification_settings` on every new rule as a checklist item. The contact
> point is `provenance: "api"` → **UI-locked**, editable only via the API.
> Until one lands, **the rule-#5 trap is armed.**

This is the shape [[concepts/never-widen-a-gate]]'s cousin rule names: *a
gate's release condition must never depend on the thing it blocks.* Here the
alerting plane's default is **silence**, and correctness is opt-in per rule.

## 2. The instrument lesson — the endpoint that hides half the routing tree

**Recurrence #8, filed on [[concepts/the-method]].** Mid-session, a confident
suspicion formed that the §1 fix was **cosmetic** — that it had merely "moved
the null one layer down," because `/api/v1/provisioning/policies` showed a
root route still pointing at receiver `empty`. That suspicion was **REFUTED
by four independent routes**, and the reason it formed at all is the finding:

**`/api/v1/provisioning/policies` does not render Grafana's autogenerated
routes.** The full Alertmanager config
(`/api/alertmanager/grafana/config/api/v1/alerts`) shows a
**simplified-routing autogen subtree** under root:
`__grafana_autogenerated__ = true` → child
`__grafana_receiver__ = grafana-default-email` → the real receiver. The
provisioning view is a **partial projection** of the routing tree, and it
omits exactly the part that makes per-rule overrides work.

The four corroborating routes (all reads 2026-08-30T22:38–22:44Z, Grafana
13.3.0-32244229338.patch1, stack ns `stacks-1722437`) [K]:

1. `/api/v1/provisioning/contact-points` → exactly ONE contact point,
   `grafana-default-email`, uid `cfs1d30a113b4c`, type email, **1
   integration**, `addresses` = the operator's real address (verified by
   string equality in memory, never printed).
2. the full AM config → the autogen subtree above; receiver `empty` is real
   and has **zero** `grafana_managed_receiver_configs`.
3. k8s API `.../namespaces/stacks-1722437/receivers` → `empty` = 0
   integrations, `grafana-default-email` = 1.
4. **the runtime's own testimony** (`/api/prometheus/grafana/api/v1/rules`):
   live alert instances for all 4 rules already carry the labels
   `__grafana_receiver__: grafana-default-email` +
   `__grafana_autogenerated__: true` — Grafana attaches the matcher labels
   **at evaluation time**, not merely in stored config. All 4 rules
   `isPaused=false`, `health=ok`; zero mute/active time intervals anywhere.

**The lesson, stated so it generalizes:** the config was right and the
**instrument's VIEW was partial**. Route 4 is the one that settled it, and it
is the [[concepts/the-method]] Stage-5 move — *ask the running system* — not
another read of a config endpoint. **A partial view and a broken config are
observationally identical from inside the partial view**
([[concepts/observational-equivalence]]).

## 4. MLSEC-1 — the tamper gate positively attests a forged artifact

**New, docketed, NOT fixed** — the fix is **cohort-resetting** (a naive
tightening refuses every unregistered or hand-trained model), so it waits on
operator adjudication. Full registration:
[[synthesis/owed-measurements]] **item 108**.

**Root cause, after an adversarial re-verify that RE-ROOTED a shallower
first diagnosis** — and the re-root made the finding *worse*, not milder,
which is why it is filed this way: `ml/registry.py` `_record_hash` (`:64`,
used at `:143` and `:209`) is an **UNKEYED public sha256**. Anyone who can
write the ledger can also write a **valid chain over forged content**.
Measured forged-chained-row case: append ONE well-formed `registered` row
whose `sha256` is the SWAPPED artifact and whose `prev` is the last row's
`h` →

```
verify_chain() -> {'ok': True, 'rows': 3, 'chained': 3, 'reason': 'chain intact'}
verify()       -> ok=True
```

The swapped artifact is **not merely un-rejected; it is POSITIVELY
ATTESTED.** [K]

**Two weaker symptoms sit on top and must not be mistaken for the disease.**
`ml/meta_model.py:83` rejects only on `v.get("ok") is False`, while
`registry.py:284-287` / `:221-222` return `ok=None` for absent pedigree or an
unreadable ledger. Injection-confirmed with controls: ledger intact →
`ok=False`, ML-011 fires, `p_win` falls back to the prior **0.5600**; ledger
deleted → `ok=None`, the swapped artifact **LOADS**, `p_win` = **0.9500**, the
hard-clip ceiling, on every entry. And an **EMPTY ledger passes
`verify_chain()` vacuously** (0 rows = "chain intact"), so the verifier cannot
distinguish *untampered* from *no evidence*.

**Consequence for the fix, so it is not UNDER-fixed:** *"reject on `ok is not
True`" DOES NOT CLOSE THIS.* That covers only the `ok=None` path; a forged row
returns `ok=True` and sails through any such check. **A keyed MAC, or an
out-of-tree signer, is the class of fix; nothing weaker is a fix.**

**Threat model, so it is not OVER-fixed — and this is the honest half.** The
[HIGH] severity rests on a **PARTIAL-WRITE** attacker: one who can write
`outputs/models/` (a hostile artifact drop, a stray process, a botched sync)
but does **not** own the repo. **Against an attacker who already owns the
repo, no gate here helps** — `registry.jsonl` lives in the *same directory*
as the artifact it attests, and the verifier itself is editable. Filed with
the severity conditioned on the model rather than asserted flat.

This is the **fifth** recorded instance of the durable rule *a gate's release
condition must never depend on the thing it blocks* — the same shape as §1's
alerting default. Live state healthy as of **2026-08-30T22:52:02Z** (chain ok,
177 rows, deployed artifact `1ee3ae68c0df` verifies `ok=True`) — **a snapshot,
not a standing property.**

## What this session could NOT see

- §1 stops at the **mailer's acceptance**. Inbox-vs-spam and mailbox
  monitoring are unmeasured (owed 109). "Delivery is proven" means proven to
  the routing layer plus one accepted handoff, and nothing further.
- §3's count is a **snapshot** and decayed within 23 minutes of being taken.
  Every number in it is as-of, never current.
- §4 is a **read-only** audit of `execution/` + `ml/`. It found what it looked
  at; the OWED-VERIFY register in `docs/HANDOFF.md` names the lanes it did
  **not** cover, and a "0 findings" that was never run is not a finding.
- Nothing here measures the strategy. Era-6 accrual is 4 trips and the
  moratorium forbids reading rates off it.
